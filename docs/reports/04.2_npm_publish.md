# Task 04.2 — npm packages, self-contained typed client, bootstrap API key (v0.4.2)

## Summary

The scraping library and the typed client are ready to go on npm as **`@reconsumet/core`** and
**`@reconsumet/client`**. Nothing was published: you do the first publish by hand (steps below), and after that every
`v*` tag publishes them from GitHub Actions with npm trusted publishing (no token stored anywhere).

The client used to drag the whole API server in (database layer, zod, the native TLS library) just for its types.
Now it installs with only `hono`, and its types are still fully real. A new check (`pnpm test:pack`) proves both things
by installing the packed client into a fresh npm project outside the workspace.

The API can also create an API key by itself: set `API_BOOTSTRAP_KEY` (32+ characters) and the API makes sure that
key exists on every start. That means the site's compose stack (task 05) can come up with a working key and no CLI
step. The old `keys create` CLI still works.

Checked on the PC: lint, typecheck, all tests (core 162, relay 24, db 12, api 15, client 1), build, `pnpm test:pack`
and `node scripts/publish-npm.mjs --dry-run`. Checked **on tsss-server** (the PC has no Docker): both Docker images
build, and the built API image created the bootstrap key on first start against a real Postgres 17, left it alone on
restart, accepted it (200) and refused a wrong key (401). The key never appeared in the logs. The test containers,
images and temp folder were removed afterwards.

## How the client's types became self-contained

**No dts bundler.** The task suggested `tsdown`/`rolldown-plugin-dts` or `rollup-plugin-dts`. Neither fits:

- The repo is on **TypeScript 7.0** (the Go compiler). Its npm package has no classic JS compiler API, which
  `rollup-plugin-dts` needs.
- `rolldown-plugin-dts` would bundle `AppType = ReturnType<typeof createApp>` together with `createApp`'s whole
  declaration. That includes its parameters (`Db` → drizzle/postgres types, `Source` → core). The client's `.d.ts`
  would then import drizzle and friends again, or carry them inlined.

The fix uses `tsc` itself (`packages/client/src/index.ts`). The client takes the route table out of `AppType` with an
inline conditional type, `ServerApp extends Hono<infer _E, infer S, infer _B> ? S : never`, and gives it to an inferred
`const`. tsc then has to print the resolved type in `dist/index.d.ts`, and those route types are plain objects there
(no aliases), so they come out written in full. The emitted `index.d.ts` (437 lines) imports only `hono`,
`hono/types` and `hono/client`. It never mentions `@reconsumet/*`, zod or drizzle. The cost is one dead line at
runtime (`const routes = (() => null)()`), which has a comment explaining it. No new dependency was added.

- **Dependencies:** `hono ^4.13.21` as a regular `dependency`, the same range the API is built with. The client uses
  it at runtime (`hc`) and its types use `hono`'s `Hono`/`Client`. A peer dependency would only make sense if the site
  had to share one `hono` instance, and it doesn't. `zod` is gone: the types are plain objects.
- **`@reconsumet/api` is a devDependency only** (that's where the types come from at build time). `core` and `db`
  weren't needed even as devDependencies.
- **Zod schemas are no longer exported.** They existed only for optional runtime validation, and keeping them would
  bring back zod + `@hono/zod-openapi`. The client now exports **types only**: `CatalogEntryT`, `AnimeT`, `SourceT`,
  `EpisodesT`, `StreamsT`, `ApiError` (the same names as before, now derived from the route table), plus `ApiSchema`,
  `AppType`, `Client` and `ClientOptions`. The in-repo client test now imports `StreamsSchema` straight from the API's
  source.
- `createClient` is annotated `: Client` (`ReturnType<typeof hc<AppType>>`), so the `.d.ts` doesn't print the
  expanded client a second time.

**`pnpm test:pack`** (`packages/client/scripts/test-pack.mjs`, root script `pnpm test:pack`, run after `pnpm build`)
does the following:
1. `pnpm pack`s the client into a temp folder under the OS temp dir (outside the workspace).
2. Runs plain `npm install <tarball> typescript@^7` there.
3. Fails if `node_modules/@reconsumet/{api,db,core,relay}` exists.
4. Typechecks a file that calls `search`, `anime`, `episodes` and `streams` with `strict` and **`skipLibCheck: false`**,
   so an unresolved import in the client's `.d.ts` would fail too. The file has six `@ts-expect-error` lines (unknown
   fields, a nullable assigned to `string`, a number assigned to `string`, a bad `audio` value, an unknown route). If
   anything were `any`, those lines would become "unused" errors.

Result on the PC: `node_modules: @reconsumet, @typescript, hono, typescript` (`@reconsumet` holds only `client`),
`typecheck ok: results are typed, wrong fields fail`.

## Publish script and release workflow

`scripts/publish-npm.mjs` (no new dependencies) works like this:
- It refuses to run on a dirty tree or with mismatched versions (one clear line, exit 1).
- It runs `pnpm build`. Then, for core and client in turn: `npm view name@version`, and if it's already there it
  prints "already on npm, skipped". Otherwise it runs `pnpm pack` and `npm publish <tarball> --access public` with
  `--dry-run`/`--tag` passed through.
- Each package gets its own line (`…: published` / `dry run ok` / `FAILED — …`). Exit code 1 if any package failed.

Dry-run output (PC, logged out of npm): both packages `dry run ok` (npm warns that a real publish needs a login).
I checked the dirty-tree refusal: `publish-npm: working tree is dirty: commit or stash first`.

`.github/workflows/release.yml` has a new job **`npm`**:
- It runs on `ubuntu-latest` with `permissions: id-token: write, contents: read` for that job only.
- Steps: Node 26 via `actions/setup-node` with `registry-url: https://registry.npmjs.org`, then
  `npm install -g npm@latest`, `pnpm install --frozen-lockfile`, build, test, `node scripts/publish-npm.mjs`.
- The image job is unchanged. I didn't trigger any workflow.

## Bootstrap API key

- `API_BOOTSTRAP_KEY` (optional): when set, it must be at least 32 characters, or the API refuses to start with
  `API_BOOTSTRAP_KEY must be at least 32 characters (openssl rand -base64 32), or empty`.
  `API_BOOTSTRAP_KEY_NAME` defaults to `bootstrap`. `API_BOOTSTRAP_KEY_RPM` is optional and must be positive (empty
  means the normal key limit).
- On start, right after migrations, the API calls `ensureApiKey` (`packages/db/src/ops.ts`), which does
  `INSERT … ON CONFLICT (key_hash) DO NOTHING`. Only the SHA-256 is stored, as before. The log says `bootstrap API key
  "<name>" created` or `bootstrap API key already present`, never the value.
- **A revoked bootstrap key stays revoked** across restarts (its hash is still in the table). To replace it, set a new
  value. This is documented.
- Tests: `packages/db/test/stores.test.ts` covers created once, idempotent on a second call, only the hash stored,
  rate limit applied, and a revocation that sticks. `packages/api/test/api.test.ts` covers a too-short key rejected,
  a bad RPM rejected, and the key off by default. Plus the real-Postgres run on tsss-server described above.
- Documented in `docs/self-hosting.md` (keys section + env table), `docs/api.md` (keys + CLI section) and
  `.env.example`.

## For the site (task 05)

- Install: `npm i @reconsumet/client@^0.4.2` (or `pnpm add`). Its only dependency is `hono` (^4.13.21), which comes
  along automatically.
- Import: `import { createClient, type StreamsT, type AnimeT, type EpisodesT, type CatalogEntryT } from
  '@reconsumet/client'`.
- Key: `createClient(process.env.RECONSUMET_URL, { apiKey: process.env.RECONSUMET_API_KEY })`, on the **server
  only**. It sends `x-api-key`. In a combined compose stack, generate one value (`openssl rand -base64 32`) and give
  it to the API as `API_BOOTSTRAP_KEY` and to the site as its key variable.
- Calls: `api.v1.search.$get({ query: { q } })`, `api.v1.anime[':anilistId'].$get({ param: { anilistId } })`,
  `….episodes.$get({ param, query: {} })`, `….episodes[':episode'].streams.$get({ param, query: { audio: 'sub' } })`.
  Path params are strings. Check `res.ok` (or `res.status === 200`) before `res.json()` to get the success type.
- Minimums: Node ≥ 26 (`engines`, a warning only on npm), `moduleResolution` `nodenext` or `bundler`. Only
  TypeScript 7 was tested (`test:pack`); older TypeScript wasn't checked. The site's tsconfig needs DOM or `@types/node` for
  `fetch`/`Response`.
- No zod schemas from the client. If the site wants runtime validation, it should define its own.
