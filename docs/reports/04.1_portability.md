# Task 04.1 — portability pass (v0.4.1)

## Summary

Someone who has never heard of tsss-server can now clone the repo, set two secrets, run `docker compose up -d` and
have a working API and relay. I tested exactly that on a fresh clone. The code was already mostly generic. What tied
it to the user's setup was the deploy guide (his LAN IP, his domains, Coolify, his router), a bandwidth default sized
to his 37 Mbit/s upload, required URL settings, and the playback probe pointing at his site. All of that is now config
with neutral defaults or a placeholder in an optional example.

What's new for a stranger:
- **`compose.yaml` is the main path**: Postgres + API + relay, restart policies, healthchecks, ports bound to
  `127.0.0.1` by default, and an optional **`caddy` profile** for automatic HTTPS.
- **`docs/self-hosting.md`**: quick start, three ways to put HTTPS in front (Caddy, your own proxy, Cloudflare or a
  tunnel for the API only), three places for the relay (own hostname, a path on one domain, another machine),
  bandwidth sizing, upgrades, backups, running without Docker, and every env var.
- **Prebuilt images**: `release.yml` publishes `ghcr.io/thesupersupersigma/reconsumet-api` and `…/reconsumet-relay`
  for amd64 + arm64 when a `v*` tag is pushed. `ci.yml` runs lint, build, typecheck, tests and a Docker build on every
  push and PR. Neither has run yet: they only run once you push.
- `pnpm dev` runs API + relay without Docker on any OS (checked on the Windows PC).
- New setting `CLIENT_IP_HEADER` (e.g. `CF-Connecting-IP`), read only from `TRUSTED_PROXIES`.

I pushed back on three things and left them out:
- A data-dir volume. The API and relay write nothing to disk; everything is in Postgres. Only the dev CLI uses
  `RECONSUMET_DATA_DIR`.
- A second Caddyfile for the path-prefix setup. It's a five-line snippet in the guide instead.
- A relay-only compose file. `docker compose up -d relay` on the other machine does the job.

Fresh-clone test: **on tsss-server over the LAN** (there's no Docker on the PC), on ports 18480/18481. Everything I
started there has been removed. `pnpm dev`: **on the PC**, against a temporary Postgres on tsss-server, also removed.
Tests, typecheck, lint and build: **on the PC**.

## What a stranger needs

Requirements: Linux on x86-64 (any CPU) or arm64, Docker Engine and the Compose plugin. For public access: DNS names
pointing at the machine and ports 80/443 open.

```sh
git clone https://github.com/thesupersupersigma/RECONSUMET.TS.git && cd RECONSUMET.TS
cp .env.example .env                 # set POSTGRES_PASSWORD and RELAY_SECRET (openssl rand -base64 32)
docker compose up -d                 # add --profile caddy (+ API_DOMAIN, RELAY_DOMAIN) for automatic HTTPS
curl http://localhost:8080/v1/health
docker compose exec api node dist/cli.js keys create mysite
```

Prebuilt images instead of building: `docker compose pull && docker compose up -d` (this works once `v0.4.1` has been
pushed and the GHCR packages are public, see below). Without Docker: `pnpm install`, put `DATABASE_URL` and
`RELAY_SECRET` in `.env`, then `pnpm dev`.

## arm64

It should work, but it hasn't been run on real arm64 hardware yet.
- The only native dependency in the images is wreq-js 3.2.0, and it ships `@wreq-js/binding-linux-arm64-gnu`, which is
  in the lockfile. Everything else is plain JS. `node:26-bookworm-slim` and `postgres:17-bookworm` are multi-arch.
- `release.yml` builds `linux/arm64` under QEMU. I didn't build it locally: there's no Docker on the PC, and setting up
  QEMU binfmt on tsss-server changes the host's kernel settings, so I left that alone. The first release run will be
  the first arm64 build.
- If it fails, the fallback is to drop `linux/arm64` from `release.yml` and say why in the README.

## For your own deployment

Your Coolify setup keeps working, but check two defaults that changed:
- **Set `RELAY_GLOBAL_MBPS=32` on your relay.** It was the default before and is now off unless set.
- **Check `TRUSTED_PROXIES` on both services.** `.env.example` used to preset `172.16.0.0/12`; it's now empty by
  default.

The Cloudflare-Tunnel API can also use `CLIENT_IP_HEADER=CF-Connecting-IP`. Your real values belong in your private
env files only.

## What the site (0.5) must do to stay portable

- **All addresses from env** (API URL, relay URL, its own public origin), with `localhost` defaults. Never derive the
  site URL from the `Host` header.
- **The API key stays server-side** (env). The relay origin check needs the site's origin in `RELAY_ALLOWED_ORIGINS`;
  document that pairing.
- **Add the site to the same `compose.yaml`** (a `site` service, plus a hostname in the Caddyfile). Keep its own
  Postgres database or schema configurable, and make it run on amd64 + arm64. Avoid native deps that lack arm64
  prebuilds.
- **No Cloudflare/Coolify/Vercel-only features** (no edge runtime, no `CF-*` headers assumed). Use the same
  `TRUSTED_PROXIES` / `CLIENT_IP_HEADER` pattern for client IPs.
- **Branding, domain, Discord link and analytics come from config**, so a self-hoster isn't running "your" site.
- **Build its images in the same `release.yml`** (`reconsumet-site` or similar) and add CI for it.
